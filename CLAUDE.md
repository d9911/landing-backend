# Архитектура проекта: Clean Architecture + Feature Modules (DDD-lite)

Этот документ описывает структуру и принципы организации кода backend части проекта, реализованные в соответствии с Clean Architecture и идеями Domain-Driven Design (DDD-lite), а также кратко описывает frontend структуру (FSD-lite).

## 🧱 Backend (Node.js + Express)

### Слои架构 (Clean Architecture)

```
src/
├── app/                 # Точка входа (Express сервер, роуты, middleware)
├── features/            # Бизнес-логика по функциям (Feature Slicing)
│   └── feedback/        # Пример фичи: обработка обратной связи
│       ├── dto.ts       # Data Transfer Objects (валидация входных данных)
│       └── useCase.ts   # Интерактор (Use Case): содержит бизнес-логика фичи
├── infrastructure/      # Технические детали (транспорты, клиенты, репозитории)
│   └── mail/            # SMTP транспорт через nodemailer
│       └── transporter.ts
├── shared/              # Общие утилиты, конфиги, типы
│   └── config/          # Загрузка конфигурации из .env
│       └── index.ts
└── server.ts            # Точка запуска (Express app)
```

#### Основные принципы:

1. **Разделение ответственности (Separation of Concerns)**  
   - Внешние фреймворки (Express) изолированы в слое `app`.
   - Бизнес-логика не зависит от инфраструктуры (например, nodemailer используется только в `infrastructure/mail`).

2. **Dependency Rule**  
   - Внутренние слои mogą зависеть только от других внутренних слоев (или общих).  
   - Внешние слои (frameworks, drivers) не знают о внутренней логике.

3. **Feature Modules (DDD-lite)**  
   - Каждая бизнес-функция вынесена в отдельную папку под `features/`.  
   - Внутри фичи: DTO (данные), Use Case (логика), потенциально репозитории (если нужны БД).

4. **Порты и Адаптеры (Ports & Adapters)**  
   - Транспорт SMTP реализован как адаптер в `infrastructure/mail`.  
   - Use Case зависит от абстракции (в данном случае — готового `transporter`), но можно легко заменить на другой транспорт (например, SendGrid) без изменения бизнес-логики.

### Пример использования: отправка обратной связи

1. **Запрос приходит в роут** (`src/app/routes/feedback.ts` – пока инлайновый в `server.ts` для простоты).
2. **Контроллер** вызывает `sendFeedbackUseCase` из `features/feedback/send/useCase.ts`.
3. **Use Case**:
   - Валидирует входные данные через DTO.
   - Формирует два письма (владельцу и пользователю).
   - Последовательно отправляет их через `transporter` (с задержкой и обработкой ошибок).
4. **Транспорт** (`infrastructure/mail/transporter.ts`) создает nodemailer транспортер на основе конфигурации из `shared/config`.
5. **Конфигурация** загружается через `dotenv` и поддерживает переключение между primary/secondary SMTP через переменную `SMTP_METHOD`.

### Обработка ошибок и gracefull degradation

- При отправке письма пользователю (некритичная копия) ошибки ловятся и приводят к предупреждению, но не падает весь запрос.
- Основная транзакция (письмо владельцу) считается критической – при её ошибке запрос падает с 500.

## 🎨 Frontend (FSD-lite)

Frontend реализован без фреймворков, следуя принципам Feature-Sliced Design (FSD) в упрощённом виде:

```
frontend/
├── src/
│   ├── assets/          # Статические ресурсы (изображения, иконки)
│   ├── features/        # Бизнес-фичи (например, форма обратной связи, голосовой ввод)
│   │   └── feedback-form/
│   │       ├── index.html   # Шаблон (или через JS)
│   │       ├── script.js    # Логика фичи
│   │       └── style.css    # Стили (БЭМ)
│   ├── shared/          # Общие утилиты, компоненты, константы
│   │   ├── ui/          # Переиспользуемые UI-элементы (кнопки, модалы)
│   │   └── lib/         # Утилиты (валидация, запросы к API)
│   └── main.js          # Точка входа: инициализация приложения
```

### Основные подходы:

- **Модульный CSS** через БЭМ-нейминг, стили расположены рядом с компонентом.
- **Нет глобальных состояний** – взаимодействие между фичами происходит через кастомные события или простой pub-sub при необходимости.
- **Web Speech API** инкапсулирован в отдельную фичу voice-input, не влияет на остальное приложение.

## 🛠 Как запустить

### Локальная разработка

```bash
# Клонировать репозиторий
git clone <repo-url>
cd landing-backend

# Установить зависимости и запустить оба сервера
make dev
# То же самое, что и: npm run dev
```

### Добавление переменных окружения

Скопируйте пример и настройте под себя:

```bash
cd backend
cp .env.example .env
# Отредактируйте .env, указав реальные SMTP данные или оставив mailtrap для теста
```

### Переключение SMTP методов

В `.env` установите переменную:

```
SMTP_METHOD=primary   # Mailtrap (по умолчанию)
# или
SMTP_METHOD=secondary # Mail.ru (нужен пароль приложения)
```

Смотрите `.env.test` для примеров обеих конфигураций.

### Production сборка

```bash
make build   # Собирает бэкенд (TS → JS) и фронтенд (vite build)
make prod    # Запускает production версии (требует предварительной сборки)
# или отдельно:
#   make start-backend && make start-frontend
```
